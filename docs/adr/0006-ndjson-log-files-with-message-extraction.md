# Structured logs are stored as NDJSON and discovered via message extraction

Log files can be NDJSON (one JSON entry per line) as well as plain text, detected per file by the pipeline — the capability belongs to the pipeline, not to any import provider, so hand-uploaded NDJSON files get the same treatment as imported ones. Imported GCP entries land in a fixed envelope: `{"ts": ..., "severity": ..., "payload": {...}}` with the jsonPayload nested untouched (textPayload becomes `payload.message`); provider metadata such as labels, trace, and resource stays in the ImportRun record, not in the log lines.

For pattern discovery, a text line is extracted from each JSON entry rather than feeding Drain the whole entry: the first string field among `_msg`, `message`, `msg`, `log`, `error` of the payload becomes the extraction; if none exists, the compact payload JSON is the fallback. The severity (`severity`, then `level`) is kept out of the extraction and stored with the entry, so the same log mines to the same templates whether it is exported as text, CSV, JSON or NDJSON; it sets the pattern's level instead. Runs mined before this have level-prefixed templates and are not read (discovery run format 2); those logs have to be imported again. Date-times and UUIDs (a comma-separated list of UUIDs as one) in the extraction are masked to `<*>` before mining, as in plain-text bodies (discovery run format 3). `_msg` is the VictoriaLogs message field, so VictoriaLogs query results are read as is. Because `_msg` is checked first, a plain JSON line that has both `_msg` and `message` now yields `_msg`. Timestamps are excluded from the extraction to keep Drain templates clean; the first RFC 3339 string among the top-level `_time` (VictoriaLogs) and `ts` (import envelope) fields is kept as the entry timestamp for time-based metrics, so imported GCP entries get time ranges and buckets too.

Grafana Explore logs exports (Download as JSON: one top-level array, newest first; Download as CSV: a `Date`/`Time`/`Line` header with quoted multi-line bodies) are normalized to NDJSON when a file lands in `logs/` (add-log, web upload, `lapp <file>`, `lapp summary`), not at read time: the stored file then has one entry per line, so line references, jq-style queries, and the existing NDJSON detection and extraction all apply unchanged. Each entry becomes `{"_time": ..., "level": ..., "_msg": <line>, "fields": {...}}` in chronological order; `_time` comes from the nanosecond `timestamp` (JSON) or `Date` (CSV), falling back to `date` or the millisecond `Time`; `level` comes from `detected_level`, `severity_text`, or `level`; the export fields stay nested under `fields`. A file that only looks like an export but does not parse as one is stored unchanged. Grafana's text export stays text; only its summary lines (`<n> lines shown`, `Common labels: ...`) are dropped on landing. See `pkg/ndjson/grafana.go`.

Entry boundaries: in NDJSON one record is one entry, even when its message spans several lines (multi-line SQL plans); multiline detection never runs on structured files. In plain text, an entry starts only at a line whose leading timestamp has the file's dominant shape (`logheader.StartShape`, e.g. `<epoch>\t<ISO>\t` for the Grafana text export); timestamps mid-line or in another format stay continuation lines. When at least 5% of the non-blank lines (and at least 3) are entry starts, the lines after each start join it, capped at 2000 lines or 1 MB per entry (the overflow starts a new entry and is counted); below that the file is split one line per entry. The DiscoveryRun records `split_mode` (`MERGED` or `PER_LINE`), `physical_line_count`, and `capped_entry_count` so the page can say how lines were split.

**Considered Options**

- Flatten everything to text at import time (structure lost)
- NDJSON storage, discovery on compact-JSON lines (structure kept, dirty templates)
- NDJSON storage with message extraction (chosen)
- JSON-native pattern discovery by structure/key-set (a second discovery engine — deferred, not rejected)

**Consequences**

The envelope and the extraction rule are part of the workspace file contract (ADR 0001). Payload fields are never flattened to the top level, so user fields named `severity` or `ts` cannot collide with the envelope. Analysis agents can query structure with jq-style tools instead of grepping flattened text. If real usage shows dirty templates for payloads without a message-like field, the extraction rule is the extension point.
